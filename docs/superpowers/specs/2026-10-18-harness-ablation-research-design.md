# Harness 组件因果消融与预算感知选择：研究设计

## 1. 研究定位

### 1.1 暂定题目

**Which Harness Capabilities Matter? A Causal Study of Agent Harness Primitives under Fixed Budgets**

中文暂定题目：**面向长时智能体的 Harness 组件因果评测与预算感知配置选择**。

### 1.2 背景与缺口

Prime Agent 将持久 IPython REPL、递归子 Agent、daemon-backed 会话和 Continual
Harness 组合成面向长时任务的执行底座。现有论文证明了这套系统能够承载大规模测试时计算，
但没有分别关闭关键组件，也没有隔离各组件及其交互项的贡献。因此，现有证据不能回答：

- 持久 REPL、递归子 Agent 和持久 Harness 分别在什么任务条件下有效；
- “所有能力始终开启”是否优于更小、更便宜的配置；
- 能否在任务开始前，根据可观察特征和预算选择合适配置。

本研究填补该缺口。研究不训练或微调大模型，而是在固定模型、provider、prompt 模板和预算的
条件下，对真实 Prime Agent 中的 Harness 能力进行随机化干预和配对评测。

### 1.3 核心论点

Harness 能力的收益具有任务异质性和组件交互。“功能全开”不是普遍最优策略；一个只使用运行前
静态特征的轻量配置选择器，可以在不降低任务质量的前提下减少 API 成本，或在相同预算下提高
任务质量。

### 1.4 研究问题

- **RQ1：组件效应。** 持久 REPL、递归子 Agent、持久 Harness 对任务成功率、验证器得分、
  token、费用和延迟分别有什么影响？
- **RQ2：异质性与交互。** 组件效应是否随任务结构变化？组件之间是否存在协同或抵消？
- **RQ3：预算感知选择。** 能否仅根据运行前可见的任务特征和预算，选择优于固定配置的
  Harness 组合？
- **RQ4：迁移风险。** 持久 Harness 在重复任务中何时产生正迁移，何时固化错误经验并产生
  负迁移？

### 1.5 可检验假设

- **H1：** 持久 REPL 主要改善需要搜索、聚合、反复计算和跨 turn 保留中间状态的信息密集任务。
- **H2：** 递归子 Agent 主要改善可分解且执行链较长的任务；在短任务中，通信和额外上下文会
  增加成本并可能降低成功率。
- **H3：** 持久 Harness 对同分布的重复任务产生正迁移，但错误 refinement 会产生可测量的
  负迁移。
- **H4：** 任务条件化选择器能在成功率无显著下降时，比所有能力开启节省至少 20% API 成本，
  或在相同成本约束下显著提高验证器得分。

### 1.6 贡献边界

本研究计划贡献：

1. 真实 Prime Agent 上的可控 Harness 组件干预层；
2. 三类具有自动验证器、分别激活不同能力的任务；
3. 组件主效应、交互效应、成本收益和负迁移的配对实验；
4. 无需训练大模型的预算感知配置选择器；
5. 可复现的 manifest、运行记录、分析代码和去敏汇总结果。

研究结论只声称在所测模型、provider、任务分布和预算范围内具有因果解释，不外推为所有 Agent
系统或所有任务的普遍规律。

## 2. 实验处理

### 2.1 三个二元变量

| 变量 | 开启处理 | 关闭处理 |
| --- | --- | --- |
| R：持久 REPL | Python namespace 跨 settled turn 保留 | 每个 settled turn 后清空 namespace；同一 turn 内仍可正常执行 Python |
| S：递归子 Agent | 允许 `rlm.spawn` 创建后代会话 | 在 admission 边界拒绝创建后代会话 |
| M：持久 Harness | 允许读取、注入和写入实验 Harness 状态 | 使用空 Harness，不注入 digest，并拒绝 refinement 写入 |

三项处理形成完整 `2³ = 8` 因子矩阵。每个处理必须从运行开始生效，且在会话记录中留下稳定的
配置标识。

R 关闭时仍允许模型使用文件系统保存中间结果。这使估计结果代表“持久 REPL 相对于已有文件工具
的增量价值”，而不是人为禁止所有外部状态后的最大效果。该选择更接近真实 Agent 环境，也使效应
估计更保守。

M 的迁移实验使用一系列彼此独立的新会话。M 开启时，只有显式 refinement 产物通过实验专用
Harness store 进入下一 episode；M 关闭时，下一 episode 使用空 store。历史对话、先前工作目录和
先前输出不直接提供给新会话，从而把跨 episode 差异限定为持久 Harness 处理。

### 2.2 固定条件

以下因素在同一实验区组内保持一致：

- 模型 ID、provider、service tier 和 reasoning level；
- 基础 prompt、任务 prompt 和工具定义；
- compaction 策略与阈值；
- 最大输出 token、总 billable token、费用和 wall-clock 限制；
- API 快速重试、provider failover 和基础设施重试规则；
- 工作目录初始快照、任务资源和 verifier 版本。

组件关闭时，系统提示只删除或替换对应能力说明，避免诱导模型反复调用不可用能力。除此之外的
静态和动态提示保持字节级一致。能力说明差异被视为处理的一部分，因为可用接口与其说明共同构成
Agent 可观察的 Harness。

### 2.3 资源公平性

预算核算聚合根 Agent 与全部后代会话。子 Agent 的输入、输出、缓存 token、费用和 wall-clock
均归入当前任务。比较不允许多 Agent 配置获得隐藏的额外预算。

主实验使用固定总费用上限和固定最大输出 token；先触及任一上限即停止。另报告在多个预算截点下
的性能曲线，以避免单一阈值掩盖配置差异。

## 3. 任务设计

### 3.1 信息管理任务（I-Family）

每个实例提供长文档、日志或结构化记录，要求模型完成检索、聚合、关联、计算并输出精确答案。
初始材料以只读文件形式提供，与 Prime Agent 论文中的长上下文设置一致。

- 30 个主实验实例；
- 覆盖单跳检索、多跳关联、分组聚合、时间窗口计算和矛盾证据消解；
- verifier 输出 `[0, 1]` 连续得分，并提供严格 exact-match 成功标识；
- 构造过程保存答案生成程序，避免人工主观评分。

该任务族主要检验 R，并观察 R 与 S 的替代或协同关系。

### 3.2 可分解工程任务（E-Family）

每个实例是一个隔离的小型多模块代码仓库，包含 2–4 个可相对独立定位、但最终需要集成验证的
缺陷。任务只通过测试套件定义成功，不使用人工“看起来正确”的判断。

- 30 个主实验实例；
- 缺陷覆盖解析、状态管理、并发边界、错误处理和跨模块接口；
- 每个实例包含隐藏测试，公开测试只提供最低限度反馈；
- verifier 同时报告通过测试比例和全量通过标识；
- 仓库规模、测试数量和初始失败数量按层分组，避免只测一种难度。

该任务族主要检验 S，并观察 R×S 交互。所有配置使用相同 CPU、内存和测试超时。

### 3.3 跨任务迁移任务（T-Family）

任务以 episode 序列组织。同一序列共享稳定但不直接声明的操作规律、格式约束或诊断经验，具体
输入在 episode 间变化。每个 episode 使用新会话和新工作目录。

- 10 个模板，每个模板 3 个计分 episode，共 30 个主实验实例；
- 第一个 episode 允许产生 refinement，后续 episode 衡量迁移；
- 一半模板提供一致经验，衡量正迁移；
- 另一半在后续 episode 引入可检测的规则变化，衡量错误经验和负迁移；
- verifier 记录当前 episode 得分、达到成功所需费用，以及是否复用了已失效规则。

该任务族主要检验 M，并观察 R×M 和 S×M 交互。

### 3.4 外部有效性

毕业论文主实验使用上述 90 个自动验证实例。投稿扩展增加：

- 20 个长上下文公开任务，用于验证 R 的方向是否与自建任务一致；
- 12 个 SWE-bench Verified 任务，用于验证 S 在真实代码库中的表现；
- 一个独立生成、未参与任务设计和 selector 训练的迁移模板集合，用于验证 M。

公开任务只运行最小配置、所有能力开启、主实验中预测的全局最佳固定配置，以及自适应配置，
不运行完整八配置矩阵。

## 4. 实验协议

### 4.1 阶段式运行

1. **本地流程验证：** faux provider 跑通任务加载、配置注入、日志、verifier 和费用停止器。
2. **Pilot：** 每个任务族抽取 5 个实例，运行全部 8 个配置，共 120 次 API run。
3. **主实验：** 90 个实例分别运行全部 8 个配置，共 720 次 API run。
4. **随机性检查：** 每个任务族抽取 10 个实例，对关键对比增加两个重复，共 60 次附加 run。
5. **强模型验证：** 每个任务族抽取 6 个代表实例，运行四个关键配置，共 72 次 run。

Pilot 实例不进入主实验统计。正式主实验前冻结任务、manifest、预算、错误分类、主指标和分析脚本
哈希。若 Pilot 显示平均成本会突破总预算，则保持 30 个任务模板不变，降低每实例 token 上限，
而不是根据 Pilot 成绩删除困难实例。

### 4.2 随机化与阻断

- 任务是配对区组，同一任务接受全部八种处理；
- 每个任务内的配置顺序随机化；
- API run 按短时间块交错执行，减少服务端版本漂移和负载变化影响；
- 主模型与强模型分别分析，不把不同模型的原始分数直接混合；
- 支持 seed 的 provider 固定 seed；不支持时依靠任务配对和重复子集估计随机性。

### 4.3 失败分类

- **基础设施失败：** 网络中断、provider 5xx、进程启动失败、实验 runner 崩溃。按预注册上限重试，
  重试耗费单独记录但不作为 Agent 失败。
- **Agent 失败：** 无效工具调用、预算耗尽、错误答案、测试不通过、错误 refinement、Agent 自身导致
  的 kernel 或子会话异常。不得删除或无条件重跑，计入结果。
- **任务缺陷：** verifier 错误、初始仓库不满足任务前置条件、答案生成器不一致。冻结后发现时，
  对所有配置整体排除该任务，并公开排除原因，禁止只删除某个配置的失败。

### 4.4 API 漂移控制

每次运行记录模型 ID、响应中的版本信息、provider、service tier、时间、价格表版本和关键请求参数。
同一任务的八种配置尽量在同一天完成。若 provider 在主实验中更换模型版本，则把版本变化作为阻断
变量，并对变化前后分别报告敏感性分析。

## 5. 指标与统计分析

### 5.1 结果指标

主要结果：

- `Success@Budget`：预算内达到严格成功条件；
- verifier 连续得分；
- 跨 episode 的正迁移增益与负迁移损失。

次要结果：

- 根与所有后代的输入、输出和缓存 token；
- 实际 API 费用；
- wall-clock 时间；
- 模型调用、工具、kernel、子 Agent 和 Harness 操作数量；
- API、工具和进程级失败率。

效率结果：

- 每单位费用的 verifier 得分；
- 成功任务的 cost-to-success；
- 配置的质量—费用 Pareto frontier。

### 5.2 因子效应

对二元成功结果使用带任务随机截距的广义混合效应模型；对连续 verifier 得分和对数费用使用线性
混合效应模型。固定项包含 `R`、`S`、`M`、两两交互、三阶交互、任务族和预先定义的难度层。

同时报告：

- 平均处理效应和任务族条件处理效应；
- 95% 按任务聚类 bootstrap 置信区间；
- 原始配对差值分布；
- 效应量，而不仅是显著性；
- H1–H4 主检验的 Holm 多重比较校正。

“因果”仅指随机化处理在本实验任务和固定运行条件下的处理效应。API 不完全确定性、模型版本和
任务抽样共同限制外推范围。

### 5.3 预算曲线

除预注册的主预算外，在累计费用或输出 token 达到主预算的 25%、50%、75% 和 100% 时计算可验证
进度。对提前成功的运行使用最终成功状态延续；对提前失败或停止的运行保留停止时得分。该分析用于
判断某组件是提高最终能力，还是仅改变达到同一结果的速度。

## 6. 预算感知配置选择器

### 6.1 输入与输出

选择器输入只能包含执行前可见特征：

- 输入字符/token 估计；
- 文件数、模块数、公开测试数和任务类型；
- 是否声明多个独立目标；
- verifier 类型；
- 总费用和 token 预算；
- 主模型 ID。

禁止使用运行轨迹、中间 verifier 结果、隐藏测试信息或真实处理效果。输出是八种 `R/S/M` 配置之一。

### 6.2 模型与目标

主 selector 使用深度不超过 3 的梯度提升树，以预测每个配置的 verifier 得分和费用。给定预算后，
选择预测费用不超过预算且预测得分最高的配置。一个单棵决策树作为可解释性消融。

训练仅使用主模型主实验数据，不需要 GPU。超参数只在训练折内选择。

### 6.3 数据划分

- 相同生成模板的实例必须位于同一折；
- 主结果使用 leave-one-template-out 交叉验证；
- 额外报告 leave-one-task-family-out，检验跨任务族泛化；
- 强模型与公开 benchmark 完全不参与 selector 训练。

### 6.4 基线

比较：

1. 最小 Harness（R/S/M 全关）；
2. 所有能力开启；
3. 训练集上的全局最佳固定配置；
4. 获得相同静态元数据和预算说明的 LLM 自选择；
5. 学习得到的 selector；
6. 使用真实结果事后选择的 Oracle 上界。

主成功标准是：selector 相比所有能力开启，在成功率无统计显著下降的情况下节省至少 20% API
成本，或在相同成本下显著提高 verifier 得分。若 selector 未达到标准，组件效应研究仍可支撑毕业
论文，但不把预算感知选择作为正面论文结论。

## 7. 实现架构

### 7.1 产品侧干预层

在现有 session/kernel/RLM host 配置边界引入实验专用的 typed treatment：

```rust
struct HarnessTreatment {
    repl: ReplTreatment,
    subagents: SubagentTreatment,
    harness_state: HarnessStateTreatment,
}
```

每个枚举明确表达 `Enabled` 与实验关闭语义，不使用位置不明的 `bool`。处理类型由 `pa-core` 拥有；
`pa-cli` 仅在实验构建或内部运行入口中完成装配；`pa-daemon` 在子 Agent admission 和 worker create
配置中透传必要状态。正常产品默认值保持全部启用。

实验入口不新增公开用户命令，不改变既有 wire 字段、会话格式或模型可见工具名称。研究配置只通过
实验 runner 启动的内部入口进入，避免把论文实验面扩散为正式产品 API。

### 7.2 实验目录

```text
experiments/harness-ablation/
  tasks/          # 任务生成、固定实例与 verifier
  manifests/      # 模型、处理、预算、seed 和价格表
  runner/         # 并发、隔离、超时、重试、恢复和硬预算
  analysis/       # 数据校验、统计模型、表格和绘图
  schemas/        # 运行记录与汇总结果 schema
  README.md       # 从零复现实验的命令与环境说明
```

大型轨迹、API 原始响应和可能包含代码内容的数据不提交到 Git；仓库只保存 schema、manifest、去敏
汇总和可公开的小型 fixture。公开 artifact 使用内容哈希和下载说明固定版本。

### 7.3 运行隔离与幂等性

每次运行使用独立的 agent directory、session directory、工作目录和端口。稳定 run ID 由
`task_id + treatment + model + seed + manifest_hash` 生成。runner 在启动前检查完成标记和记录
schema，确保断点恢复不会重复付费。

每个 run 保存：

- Git commit、工作树是否干净和实验代码哈希；
- 任务、处理、模型、provider、prompt 和 manifest 哈希；
- 预算、token、费用、延迟和后代资源归因；
- verifier 输出、失败分类、重试历史和停止原因；
- Harness 写入摘要及其版本，不保存用户或真实项目敏感内容。

## 8. 验证与质量门

### 8.1 处理有效性

- R：构造跨 turn 变量探针，确认开启时保留、关闭时清空；
- S：确认关闭时 spawn 在 admission 层被拒绝且无后代 worker；
- M：确认关闭时 digest 为空、写入被拒绝、下一 episode 无状态泄漏；
- 组合：八种配置均有端到端 fixture，运行记录中的 treatment 与实际行为一致。

### 8.2 实验基础设施

- faux provider 覆盖无需 API 的完整运行路径；
- verifier 对正确、部分正确、错误和超时输出有固定测试；
- 费用停止器使用模拟价格和真实 usage shape 测试；
- runner 重启后只恢复未完成 run，不重复完成 run；
- 数据审计拒绝重复 run ID、缺失配置、未知价格版本和不完整后代核算；
- 分析脚本在固定 fixture 上生成稳定统计表。

### 8.3 正式运行门禁

正式 API 实验开始前必须同时满足：

1. 产品代码的相关 focused tests 通过；
2. 实验目录的单元与端到端测试通过；
3. 120 次 Pilot 的 schema 完整率为 100%；
4. 人工抽查每种处理至少两条轨迹，确认能力开关真实生效；
5. 费用估算在 5000 元硬上限内；
6. 冻结的 manifest 和分析脚本哈希已记录。

## 9. 预算

总 API 硬上限为人民币 5000 元：

| 阶段 | 上限 |
| --- | ---: |
| Pilot 与任务筛选 | 400 元 |
| 便宜模型主实验 | 2800 元 |
| 强模型代表性验证 | 900 元 |
| 重复运行与争议样本 | 500 元 |
| 故障、价格变化和补充预留 | 400 元 |

runner 在每次调用前计算当前累计实际费用与最坏情况下一次调用费用；可能突破阶段或总上限时停止，
不得依赖人工观察账单。未使用的阶段预算可进入预留，但总硬上限不变。

主实验模型从已有可用 API 中选择满足以下条件者：固定版本、结构化 usage、稳定的工具调用、价格足以
支撑 720 次主 run。强模型只运行 72 次关键配置验证。具体 provider 凭证不进入代码、manifest 或
论文 artifact。

## 11. 风险与降级路径

| 风险 | 缓解 | 降级后的可信结论 |
| --- | --- | --- |
| 组件无显著平均效应 | 保留任务配对、连续分数和任务族交互 | 报告能力无效的边界条件，不宣称普遍提升 |
| selector 不优于固定配置 | 检查校准和特征泄漏，不增加事后特征 | 以组件效应与异质性作为毕业论文主结论 |
| 自建任务过于人工 | 增加公开长上下文和 SWE-bench 子集 | 将自建任务定位为机制测试，不声称生态代表性 |
| API 不稳定或版本漂移 | 短时间块交错、版本记录、敏感性分析 | 限定结论到稳定时间块和模型版本 |
| 统计功效不足 | 配对设计、连续 verifier、聚类 bootstrap | 报告区间与效应量，不把不显著解释为无效 |
| 预算超支 | Pilot 估价、逐次计费、runner 硬停止 | 优先完成一个主模型的完整矩阵，缩减强模型验证 |
| treatment 被文件工具替代 | 保留工具调用和中间文件审计 | 将 R 解释为持久 REPL 的增量效应 |
| refinement 固化错误 | 规则变化模板、Harness 版本与来源审计 | 报告负迁移并提出 provenance/rollback 后续方向 |

## 12. 交付标准

### 12.1 毕业论文最低交付

- 三种 treatment 在真实 Prime Agent 中可验证地生效；
- 三个任务族与 90 个主实验实例；
- 一个主 API 模型的完整八配置矩阵；
- 配对因子分析、费用核算、失败分类和威胁讨论；
- 可运行的实验脚本、去敏结果和毕业论文。

### 12.2 可投稿版本

- 至少两个模型上的方向一致性检查；
- 公开任务子集的外部验证；
- selector 与五个非 Oracle 基线的严格比较；
- 配置、任务和分析 artifact 可独立复现；
- 论文明确区分受控处理效应、观察性轨迹分析和外推推测。

### 12.3 ICLR 竞争版本

ICLR 版本不能只依赖“完成了很多实验”。至少需要以下一种强结果：

- 稳定、跨模型的反直觉组件交互；
- selector 在未见任务模板和公开任务上形成明确的质量—成本 Pareto 改善；
- refinement 负迁移的系统性规律，以及经过额外验证的低成本缓解方法；
- 一个被独立使用或复现的 Harness 干预与评测 artifact。

## 13. 论文结构

1. Introduction：Harness 功能增长与因果证据缺口；
2. Related Work：agent harness、RLM、memory/refinement、test-time compute、Agent 评测；
3. Harness Treatments：R/S/M 定义、公平预算和可识别性；
4. Benchmark and Protocol：三个任务族、随机化、指标和失败政策；
5. Component Effects：主效应、交互、任务异质性和成本曲线；
6. Budget-Aware Selection：selector、基线、泛化和 Pareto 结果；
7. Negative Transfer and Safety：错误 refinement 的持续影响；
8. Limitations：API 黑盒、模型漂移、自建任务和外推限制；
9. Conclusion。

## 14. 研究责任与披露

AI 可以辅助实现、测试、分析脚本、图表和文字编辑，但研究者对假设、实验协议、数据排除、统计
解释和论文陈述承担责任。提交前按目标会议当年的政策披露 AI 使用情况。API 凭证、真实用户会话、
私有代码和含敏感内容的轨迹不得进入公开 artifact。
